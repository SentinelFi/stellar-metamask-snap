# Changelog

All notable changes to this project are documented here.

The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and the project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

One changelog covers the whole repository: `stellar-soroban-snap` and `stellar-soroban-snap-connector` are versioned and released together, because the connector pins the exact snap version it installs. Release steps are in [docs/RELEASE.md](docs/RELEASE.md).

## [Unreleased]

Nothing has been published to npm yet, so every change below is still unreleased. On the first release these entries move under a `[0.1.0]` heading, dated, and the audited commit is recorded there.

### Added

- SEP-0005 key derivation at `m/44'/148'/x'` (ed25519) from the MetaMask Secret Recovery Phrase, conformance-tested against the official SEP-0005 vectors, so the same phrase yields the same addresses as Freighter, Ledger, and Lobstr.
- SEP-0043 dapp API with Freighter-compatible semantics: `requestAccess`, `getAddress`, `getNetwork`, `getNetworkDetails`, `setNetwork`, `signTransaction`, `signAuthEntry`, `signMessage`.
- Transaction review dialogs decoded from the transaction XDR itself rather than from dapp-supplied summaries, with the raw XDR always available alongside.
- Soroban support: in-snap display-verification simulation (resource fee, required auth signers, restore requirements), decoded contract invocations, and standalone authorization-entry signing.
- Balance changes for the signing account in every Soroban review dialog, decoded from the token events the display-verification simulation reports (`transfer`, `mint`, `burn`, `clawback`) and netted per asset, outgoing first. A contract invocation otherwise renders only its function name and arguments, which are the inputs a call is authorized with and not its effects: `swap(a, b, 100, 95)` does not say whose balance moves or by how much. A simulation reporting no movement for the account says so in words, and a summary that lost an event to a decode failure or a cap says that too, since a list read as complete is worse than no list.
- Advisory pre-signing safety checks for classic transactions: unfunded destination, SEP-0029 memo-required, and multisig weight.
- Multiple accounts: an explicit registry of user-revealed SEP-0005 indices, added and switched from the snap home page, with `getAccounts` and `setActiveAccount` for connected dapps and per-request account selection through the SEP-0043 `address` option.
- Soroban token tracking (`addToken`, `getBalances`) with contract-reported metadata read via read-only simulation.
- Snap home page showing network, active account, addresses, balances, tracked tokens, and connected sites, with per-origin disconnect and token removal.
- Companion packages: `stellar-soroban-snap-connector` (typed SEP-0043 client, drop-in `@stellar/freighter-api` facade, Stellar Wallets Kit module) and a Gatsby companion dapp.
- The companion dapp is a working wallet rather than a row of buttons: an account strip with network and account switching, a balances table covering classic assets and tracked Soroban tokens, a payment form that picks `createAccount` over `payment` when the destination does not exist yet, trustline opening and closing, and account history read from Horizon. Every transaction is assembled in the page and handed to the wallet as XDR, so what the review dialog shows is decoded from the envelope rather than from anything the page asserts about it, and submission is delegated to the wallet so the demo exercises its submission path. The SEP-43 methods remain individually callable, with raw responses, in a bench panel underneath.
- The dapp's interface is rebuilt around the snap's own colorway (Stellar navy with a single gold accent, reserved for the control that opens a MetaMask dialog) and is typeset in Titillium Web, self-hosted with its SIL Open Font License 1.1 text under `packages/site/static/fonts`. Self-hosting is a security choice as much as a licensing one: the page loads no remote resource, so its Content-Security-Policy needs no third-party origin and no font CDN learns who visits a wallet page.
- Property tests over the decoders and the transaction dialog, asserting that no input throws unhandled, that rendered inline text carries no hidden characters, and that every rendering limit sets the flag the signing paths fail closed on.
- Version-consistency check (`yarn check:versions`) run in CI, covering the four files that carry the release version.
- Documentation site (`yarn build:docs`, deployed to GitHub Pages by `.github/workflows/docs.yml`, which is run manually until Pages is enabled: a Pages site is public even when its repository is not, so going live should be a decision rather than a side effect of merging), rendered from the repository's own markdown by a small script rather than a documentation framework. The pages are the files, so the site cannot drift from the tree, and the published set is curated: the phase plans and research notes stay in the repository, where they read in context. Output is static HTML with no JavaScript and no remote origin, which lets it carry a `default-src 'none'` policy in a meta tag, since GitHub Pages sends no headers of its own.
- Connector API reference (`docs/CONNECTOR-API.md`), covering the typed SEP-0043 client, the Freighter-compatible facade, the Stellar Wallets Kit module, and the error codes a dapp branches on. The docs build fails when a public method of `StellarSnap` is missing from it, so a hand-written reference cannot silently describe a smaller API than the one that ships; CI runs that build on every pull request.
- Account lookup on the snap home page: enter a `G...` address or an index to reach an account you already hold in another SEP-0005 wallet. Previously the only way to reach account N was to click "Add account" N times, one confirmation each, which made the 256-account range unusable in practice. The address search derives locally over the bounded index range with no network lookup, is reachable only from the home page (never from a dapp), and the single confirmation discloses how many accounts the run reveals, since the set is kept gap-free for portability with other SEP-0005 wallets.

- Review-dialog renderers for DEX offers (`manageSellOffer`, `manageBuyOffer`, `createPassiveSellOffer`), claimable balances (`createClaimableBalance`, `claimClaimableBalance`), and liquidity pools (`liquidityPoolDeposit`, `liquidityPoolWithdraw`), so those operation types are no longer refused. Offer creation, update, and deletion are named as such; prices are shown as the exact ratio the network stores with a decimal reading alongside (the SDK's decimal decode cannot represent a non-terminating ratio); every claimant is listed with its claim condition spelled out in words; and pool operations state that the pool and its assets are identified by the pool ID alone. A claim condition of an unknown variant or nested beyond the rendering bound is refused before any dialog opens, like every other value the dialog cannot state in full.
- The snap home page shows a one-time notice when the stored settings were rebuilt from defaults, whether because the persisted store did not match the schema or because the primary Secret Recovery Phrase changed, naming what was dropped (connected sites, and for an unreadable store the account list and network) and what was kept.
- `signMessage` accepts the SEP-0043 `networkPassphrase` option and, when it is present, compares it with the active network as `signTransaction` does. The connector passes it through.

### Security

- The transaction review dialog renders the authorization entries of every `invokeHostFunction` operation, deployments included. A create-contract (V2) deployment whose constructor calls `require_auth` on the deployer carries a source-account authorization entry that the envelope signature approves; the dialog printed only the deploy parameters for that host-function kind, so a constructor's token transfer under the deployer's authority was verified as displayable by the signing gate and then never shown. One renderer now serves every kind, and the deploy banner no longer defers to the raw XDR.
- Soroban `ScString` and `ScSymbol` values, and contract function names, are rendered from their signed bytes. The decoder's UTF-8 reading replaces every invalid sequence with U+FFFD, so two different signed arguments could display identically; bytes that do not survive the round trip now render as hex, the route `manageData` keys and home domains already take.
- The snap imports no private key material to display an address or to check which Secret Recovery Phrase is primary. Every display path (`getAddress`, `getAccounts`, `getBalances`, `fund`, `requestAccess`, the home page, and the pre-dialog half of every signing request) works from `snap_getBip32PublicKey`, a new manifest permission for the same `m/44'/148'` path; the private subtree (`snap_getBip32Entropy`) crosses the sandbox boundary only to produce a signature after approval and for the user-driven account sweep on the home page. A fetched public key is confirmed against the phrase the request is bound to by a second observation after the fetch, so a phrase change overlapping a request still fails closed. Persisted fingerprints are unchanged (both routes hash the same 33-byte key).
- `setNetwork` and `setActiveAccount` are rate limited. Both have a silent success path (the target is already active) that the dialog throttle never sees, and every call costs a key request and two state decrypts.
- Token balances are accepted only as the `bigint` or safe-integer shapes a real `balance()` decodes to, within the `i128` range. A string of digits was accepted before, which handed a dapp-chosen contract an unbounded integer to parse and render on every read.
- A Horizon account body without `signers` and `thresholds` is treated as an unchecked account and disclosed as such, rather than parsing into an account with no signers that silently passed the weight check. Balance rows are validated per kind: an issued-asset row must carry its code and issuer, a pool-share row its pool ID (rendered under a new `pool` kind), and an unknown `asset_type` is refused.
- The Soroban RPC client checks the JSON-RPC `id` before believing anything in the body, error member included.
- Validation errors no longer echo the rejected value back to the caller; the path and the expectation are kept and the message is bounded. An unknown method name is echoed bounded and carries the SEP-43 `-3` code like every other refusal.
- A failure while re-rendering the home page after an interaction, or while showing the post-update notice, no longer crashes the snap (a crash resets every in-memory control: rate limits, cooldowns, the entropy-binding latch).
- The review dialog lists the read-write entries a Soroban transaction auto-restores (the signed data extension), withholds the "acts for another account" banner on a fee bump's inner transaction (the wallet signs only the fee), refuses an extra required signer key it cannot encode instead of showing a placeholder, refuses Soroban transaction data on a transaction with no Soroban operation, and treats unpaired surrogates as hidden characters so `signMessage` warns and shows the exact code point rather than signing U+FFFD unannounced. Token symbols are limited to letters, digits, dot, underscore, and hyphen.
- The publish workflow verifies the integrity of the npm it installs (the one job holding the OIDC identity), and the release build requires the tag to be annotated and its commit to be on `main`. The pre-commit hook rebuilds the manifest for lockfile and Node-pin changes too; the docs workflow uses the pinned Node.
- The connector's typed results and error recovery fields are shape-checked (strkeys, hashes, bounded base64, enumerated statuses, bounded warnings and token metadata), so a captured provider cannot hand a dapp a multi-megabyte "warning" or a signer address that is not a key.
- The companion site's post-build release check verifies two things a string search could not. Every emitted page must state the identity its configuration resolved, through meta tags rendered from the same module the browser bundle imports: searching for quoted literals was near-vacuous, because the connector ships the published snap ID and the release version as its own constants and so satisfied the search in every build, including one that fell back to the development snap. And no emitted script may still read `GATSBY_SNAP_ORIGIN` or `GATSBY_SNAP_VERSION` at runtime, which is what an unsubstituted browser bundle does: the meta tags alone cannot see that failure, since they are rendered by the server bundle, where the environment is populated whatever Gatsby did with client code. The site reuses the connector's provider discovery rather than a weaker copy, validates the `wallet_getSnaps` entry it stores, judges the version gate on the configured origin only, bounds every error message it renders, reports a trustline envelope that cannot be built instead of doing nothing, and re-probes for MetaMask when the tab regains focus. The site now has a unit-test suite for its release check and input validators.
- Fail-closed review: signing is refused for operation types, host functions, credential variants, and ScVal variants the snap cannot display faithfully, and for any value too large or deeply nested to render in full.
- Account selection requires a standing connection grant, so an origin without one cannot use resolution outcomes to test which addresses the wallet holds.
- Network passphrase pinned into every signature; a mismatching dapp-supplied passphrase is rejected.
- Dialog text sanitized against control, bidi, and zero-width characters, with an explicit warning when a rendered field differed from the signed bytes.
- Persisted state validated against a schema on every read, with prototype-chain-safe origin keys and a bounded account registry.
- State mutations serialized so concurrent read-modify-write sequences cannot drop a writer's change.
- Per-origin cooldown after repeated rejected dialogs.
- Horizon and Stellar RPC responses schema-validated, with redirects refused, bounded response bodies, and no insecure randomness in the shipped bundle (enforced in CI).
- The Soroban footprint (the signed state-access scope and resource commitment) is rendered in every Soroban review dialog, ordinary and fee-bump alike, with trustline keys naming their asset; signing fails closed when the footprint is absent, truncated, undecodable, or contains an unknown key variant.
- An asset name carried by a simulated token event is displayed only when the contract that emitted the event is that asset's Stellar Asset Contract, whose address the snap recomputes for the active network and compares. Any contract may emit a `transfer` event claiming to be `native`; without the check that would render a fabricated XLM row. A contract that fails the check still gets a row, labelled by its own address, and amounts are scaled only at a precision the snap can establish (7 for a verified Stellar Asset Contract, the stored decimals for a token the user added), never at one the contract asserts.
- The companion site verifies the installed snap version against the release it was built for before enabling any controls, offers an exact-version update when they differ, and passes the pinned version to the connector; the release build also cross-checks `GATSBY_SNAP_VERSION` against the snap package version.
- Oversized declared response bodies are released before the error is raised, and the no-stream fallback counts real bytes via `arrayBuffer` instead of UTF-16 code units.
- Persisted token registries are normalized at the parse boundary (per-network cap, contract-ID and metadata validation, duplicate removal); `fund` and `getBalances` are rate limited per origin, identical balance lookups are coalesced through a short-lived cache, and every request counts against a per-origin in-flight budget.
- Classic safety checks cover account-merge destinations, every effective operation source, and the operation-appropriate signature threshold (high for account merge and signer changes), and disclose when the lookup budget forced any account to be skipped.
- Every explicit `address` selection requires a connection grant, including the active account, so an unconnected origin can no longer probe whether a guessed address is the active one; cold signing without an address is unchanged.
- Signed messages and `manageData` keys with hidden characters get an escaped, lossless exact view, and endpoint-derived simulation and RPC error text is sanitized before reaching dialogs.
- When an origin is too long to display in full, consent dialogs and the home page show the complete origin in a copyable field with a warning, since two long origins can otherwise truncate identically.
- Submission responses are accepted only when the returned transaction hash matches the locally computed hash of the exact signed envelope.
- RPC dispatch resolves handlers as own properties only, so names like `constructor` cannot resolve inherited JavaScript properties.
- Release provenance procedure documented in `docs/RELEASE.md`: publish from the annotated tag, treat the audited ID and version as protected inputs, verify the published tarball against a rebuild, retain an attestation.
- The signing methods are rate limited per origin: their dialogs do not bound their cost, since each derives a key and `signTransaction` fans out up to seven Horizon lookups or a Soroban simulation before any dialog exists, and all three are callable without a connection grant.
- A global, origin-independent budget bounds the advisory lookups that run before a signing dialog (Horizon account checks and the display-verification simulation). Every other limit is keyed on origin, which a wildcard domain defeats by rotating subdomains; this one does not. Exhaustion is disclosed in the dialog as checks that did not run, never as silence and never as a refused signature.
- Rate-limit and dialog-cooldown tracking evicts the least recently used origin rather than the oldest, and refreshes recency on refused requests too, so an origin can no longer rotate throwaway origins to evict an active caller's counters or the record of its own cooldown.
- Muxed (`M...`) destinations, sources, and fee-bump fee sources are disclosed as unchecked instead of silently skipped, since Horizon cannot look them up and absence of a warning must never read as a passed check.
- Hidden-character detection, escaping, and inline stripping share one character class covering Unicode line and paragraph separators and the invisible fillers (U+115F, U+1160, U+17B4, U+17B5, U+2800, U+3164, U+FFA0) alongside control and format characters, so a SEP-53 message can no longer carry invisible text past the warning.
- Contract-reported token balances format correctly when negative, instead of rendering a malformed amount such as `-1.-5`.
- A transaction that sets no upper time bound is now stated as such ("No expiry: submittable at any future time", plus a warning banner) rather than rendering no validity row at all. An unbounded signature stays submittable indefinitely and the dapp holds the envelope, yet it previously displayed identically to one expiring in five minutes, because in both cases the row was simply absent.
- The global pre-dialog lookup budget is split by connection grant: unconnected origins are capped at half of it, leaving the remainder reachable only by origins the user has approved. The claim happens before any dialog opens, so a site rotating subdomains could previously drain the whole budget with no user interaction and force every other site's dialog into the "checks were skipped" state indefinitely, turning a safety caution into ignorable noise. The cold-callable surface keeps exactly the budget it had before, so its amplification bound is unchanged.
- The review dialog names the host that will receive the signed envelope when `submit` is requested, and states that it can delay or withhold submission. On PUBLIC the Soroban submission path is a third-party gateway, which a submitting user could not otherwise see.
- Contract IDs are validated by strkey checksum (`StrKey.isValidContract`) rather than by shape regex, matching the standard already applied to `G...` addresses, so a mistyped ID is rejected immediately instead of after two metadata simulations that could only fail.
- `snap_manageState` calls pass `encrypted: true` explicitly rather than relying on the SDK default, so the storage tier of connection grants and the revealed account set cannot change under a dependency bump.
- Sequence-0 transactions are no longer simulated. Their dialog branch never rendered a simulation section, so the round trip and its global budget slot were spent on a result that was discarded.
- The `Math.random` rewrite asserts the number of references it replaces and fails the build when it changes. The rewrite is textual and would also rewrite the literal inside a string constant, where the corruption would be semantic and would pass both the SES evaluation and CI's "no Math.random remains" grep.
- Auth-entry expiry is bounded against the minimum of two independent ledger-height sources (Soroban RPC and Horizon), so a single lying source can only shorten a signature's lifetime, never stretch a "five minute" default beyond what the dialog discloses. On PUBLIC the Soroban RPC is a third-party gateway and previously stood alone.
- Horizon `extras.result_codes` are passed through hidden-character sanitization before being echoed into dapp-facing error messages, matching the treatment RPC error messages already received.
- A global in-flight ceiling bounds concurrent requests across all origins, so origin rotation cannot multiply the per-origin budget; the in-flight tracking map is bounded by that ceiling instead of LRU eviction, so a live origin's counter can no longer be evicted (and thereby reset) by rotated origins.
- The connector verifies the snap version MetaMask actually installed: `connect()` compares the `wallet_requestSnaps` result against the pin and fails before any signing surface is touched, and `isInstalled()` reports false for a wrong-version npm snap.
- The connector rejects semver ranges and non-`npm:`/`local:` snap IDs at construction, so a config typo or compromised env var cannot silently unpin the audited release.
- Every typed connector method validates the response shape at runtime before dapp code receives it (previously a blind `as` cast); error `code` values outside SEP-43 map to internal, and error messages are required to be strings and length-bounded.
- EIP-6963 discovery accepts only announcements whose provider carries a callable `request`, and the comment no longer overstates what rdns matching guarantees against a page-level attacker.
- The Freighter facade no longer spreads recovery fields (`signedTxXdr`, ...) of a failed call into the result shape, where the common `if (signedTxXdr) submit(...)` pattern would submit an envelope from a failed call; recovery data now lives under `error.recovery`, an explicit opt-in.
- The companion dapp ships security headers (`static/_headers`): a CSP with `frame-ancestors 'none'`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, `X-Content-Type-Options: nosniff`, and HSTS; hosts that do not read `_headers` must replicate them (documented in `docs/RELEASE.md`). The dapp's `connect-src` names the three Horizon hosts individually rather than opening up to any origin: the account history is the only part of the page that reads the network directly, it reads from the URL the wallet reports, and that URL can only ever be one of the three. A future change that starts talking to some other endpoint therefore fails visibly in the browser instead of quietly succeeding.
- The site's post-build artifact check walks `public/` recursively (previously top-level only, missing `page-data/**`) and requires the snap origin and version as quoted string literals instead of near-vacuous substrings; `ALLOW_LOCAL_SNAP` builds emit a loud must-not-deploy warning.
- The site's one-click PUBLIC (mainnet) switch asks for confirmation before reaching the snap dialog, and the published SEP-0005 test mnemonic paragraph no longer ships in the page.
- The header connection indicator is driven by the same version-match state that gates the page controls, so a wrong-version snap shows "Update required" instead of a green "Connected".
- CI audits production dependencies of every workspace (previously snap only), runs connector tests with coverage thresholds, and generates a CycloneDX SBOM artifact on every run; Dependabot is configured for npm and GitHub Actions updates.
- `resolveSigningKeypair` derives from a single SEP-0005 parent-node fetch per request instead of two, halving sandbox-boundary crossings of parent key material.
- A connection grant check is now bound to the work it authorises, not only to the moment it ran. `assertConnected` returns a request-scoped entropy binding (the Secret Recovery Phrase fingerprint the grant was verified under, plus a state snapshot checked to carry that fingerprint) rather than a boolean, and every connected method resolves accounts through it, revalidates it after network work and before disclosing wallet-derived data or applying a side effect, and carries its fingerprint into every state write: `setNetwork`, `setActiveAccount`, `addToken`, and the home-page account switch now compare it inside the state lock, as the account reveals and `connectOrigin` already did. Explicit-address signing resolves through the same binding, so a phrase change overlapping the request is refused before any address is compared and a held address reads exactly like an unheld one. Previously a concurrent request observing a changed primary phrase could reset the store between a handler's grant check and its later reads, letting an origin connected only to the former wallet receive the new wallet's address, account list, or balances, fund its account, probe its address set through explicit-address signing, or open a wallet-global confirmation for it. The reconciliation latch is also keyed by reconciliation identity, so a phrase changing away and back cannot let the older completion vouch for the newer period, and the home page renders from the same binding's snapshot so its origins, indices, and addresses always describe one wallet. Deterministic concurrency tests cover every connected method, every signing method with an explicit address, and the change-and-change-back schedule.
- The connector's per-page version memo now covers only the public network reads (`getNetwork`, `getNetworkDetails`). `getAddress`, `getAccounts`, and `getBalances` are silent but disclose wallet addresses, the linked account inventory, and balances, so they take the fresh `wallet_getSnaps` comparison on every call like the signing methods: a replacement snap under the same npm ID holds the same granted permissions, and a memo written before the update cannot vouch for a read that would run its code over that data. A sensitive call whose own lookup is outdated by a later call's demand while it is in flight repeats the check for the newer demand instead of invoking on its older success, so two overlapping sensitive calls fail closed whichever one notices a mid-session update.
- Ledger heights reported by the Soroban RPC (`getLatestLedger`, simulation `latestLedger`) and by Horizon's root endpoint are validated as positive `uint32` sequences through one shared struct, which also rules out integers that lost precision; `boundAuthExpiration` re-checks the value before it computes an expiry and refuses a default lifetime the `uint32` expiry field cannot hold. Auth-entry expiry now requires both ledger sources on every network, not only on PUBLIC (see the entry below): range validation bounds what a sole source may report but cannot tell an inflated in-range height from a real one, so a lone test-network RPC could otherwise set the default authorization lifetime by itself while the dialog reported the fixed 60-ledger default.
- Auth-entry expiry now requires **both** ledger-height sources to answer, rather than accepting whichever one did. The bound is `Math.min` over the sources that replied, and a minimum over one value is that value, so a single Horizon failure (a 429 under load is enough) silently reduced the cross-check to trusting the third-party gateway alone. The consequence was a wrong disclosure rather than a missing one: an overstated height stretches the authorization's real lifetime while the dialog reports a duration computed from the same number, so "expires in ~5 min" could sit over an entry valid for as long as the source claimed. Test networks were at first exempt, on the grounds that both endpoints there are SDF; that exemption is withdrawn in the entry above.
- The dependency gate no longer verifies "this vulnerable package is absent from the bundle" by searching for the package name. `mm-snap build` minifies, so package names do not survive: on the 0.1.0 bundle `stellar-base` and `@noble` both produced zero hits while shipping, which means the check could not have detected axios entering the bundle, and the disposition of 30 transitive production advisories rested on it. Absence is now checked through `bundleMarkers`, string literals from each package's runtime code, and the search first proves it can find anything at all by requiring `positiveControls` from packages that certainly ship.
- `deriveFromNode` zeroes the seed copy it hands to `Keypair` once the keypair holds its own, leaving one fewer reachable copy of an account secret than it creates. A canary test fails loudly if a future SDK version starts retaining the buffer instead of copying it.
- Balance rows carry an explicit `type` (`native`, `classic`, `soroban`) and, for tokens, a separate `contractId`. Tracked Soroban tokens were rendered as `SYMBOL:CONTRACT_ID`, the same shape as a classic `CODE:ISSUER` row, with a symbol the token contract chooses: a dapp splitting `asset` on `:` and displaying the first field would show `USDC` for any contract the user was persuaded to track. The snap's own home page already avoided this by rendering tokens differently; the RPC response now carries the same distinction, and the connector's validator requires it.

- Trustline removal is recognised again: the review dialog compared the decoded `changeTrust` limit with the literal `0`, but the SDK decodes a zero limit as `0.0000000`, so removal rendered as an ordinary "Change trustline" with a plain zero row. It now reads "Remove trustline" with the warning-variant limit row.
- `manageData` keys and `setOptions` home domains are rendered from their signed bytes rather than from the SDK's decoded string. That decoder is ASCII and drops the high bit of every byte, so a key of non-ASCII bytes decoded to a clean ASCII word that passed every hidden-character check while differing from what was signed. Both fields now take the lossless text-or-hex path the `manageData` value always used, with a banner when the bytes are not plain text. Text memos take the same path, so a memo that is not valid UTF-8 (which the decoder collapses to U+FFFD) is shown as exact hex under the lossy-display banner instead of rendering identically to a different byte string.
- The hidden-character class covers the invisible nonspacing marks that `\p{Cf}` does not reach: variation selectors (U+FE00 to U+FE0F and U+E0100 to U+E01EF), the Mongolian free variation selectors (U+180B to U+180D), U+034F COMBINING GRAPHEME JOINER, and private-use code points. A memo, signed message, or contract symbol carrying them is now flagged, escaped, and stripped from inline previews like every other hidden character.
- `scvString` arguments are capped at 256 code points with an explicit `…+N chars` marker and the truncation flag the signing path refuses on, so a single string argument can no longer carry the whole envelope size limit into one dialog field where every other value shape was bounded.
- The Soroban simulation section names the RPC host that reported its figures and states that the wallet cannot independently verify them; an absent resource-fee estimate renders as unavailable instead of `0 XLM`, which claimed the call was free.
- The review dialog raises a banner when the transaction source, any operation source, or a fee bump's fee source is not the signing account, so a request to co-sign another account's envelope reads as such rather than requiring the user to compare two 56-character strings by eye. Sequence-0 challenges are exempt, since a SEP-10 challenge is sourced from the server by design.
- `setOptions` values carry their meaning: a signer weight of 0 reads "removes this signer", a master weight of 0 reads "disables the master key" with a danger banner about permanent lockout, and flags are decoded to `AUTH_REQUIRED`, `AUTH_REVOCABLE`, `AUTH_IMMUTABLE`, and `AUTH_CLAWBACK_ENABLED` (unknown bits shown as numbers), with a danger banner when `AUTH_IMMUTABLE` is being set because it cannot be undone.
- A Horizon error status, timeout, or malformed body during the advisory safety checks is disclosed as accounts that were not checked, in both the per-account checks and the fee-bump fee-source check, rather than producing zero warnings that read like a clean result. The checks remain advisory and never block signing.
- The add-token dialog labels the symbol as self-reported and unverified, names the contract address as the only identity it can vouch for, and, when the contract's reported name is `CODE:ISSUER` (or `native`) and the Stellar Asset Contract address derived for that asset equals the contract being added, states the classic asset as verified by derivation. Token and issuer labels keep six characters on each side instead of four, and every balance-change row is accompanied by its full identity (complete contract address or `CODE:ISSUER`) in a copyable field, since a shortened address is what a lookalike contract is ground to match.
- `submitUrl` on `signTransaction` is refused with code -3 and a message naming the policy: the wallet submits only to its own allowlisted endpoints, and a submission endpoint is trusted with the signed envelope. The connector refuses it client-side with the same code before MetaMask is contacted, so a caller never believes its endpoint was used.
- The embedded-authorization list in contract-invocation dialogs carries a legend saying that entries marked `[source-account]` are authorized by the transaction signature itself while entries naming an address need that address to sign the entry.
- Contract-reported token balances are accepted only as a bigint, a safe integer, or a digit string; a contract returning a boolean from `balance()` no longer displays as one smallest unit (`BigInt(true)` is `1n`).
- Stellar RPC responses must echo the request id; a body carrying a different id is refused as malformed. The unused `getTransaction` client was removed.
- The snap imports `@stellar/stellar-sdk/base` directly, so the SDK's Horizon and RPC transports (and the axios subtree beneath them) are excluded from the bundle by construction rather than by tree-shaking.
- Clean text that merely begins with `hex:` is rendered as hex by the lossless byte renderer, so the literal text `hex:00` and the single byte `0x00` can no longer display identically.
- The pinned snap version is verified by the connector on every call, not only in `connect()`: the first invocation on an `npm:` client reads what MetaMask has installed, refuses a mismatch with code -3 before the snap is contacted, and remembers a match. The Freighter facade's `isAllowed()` and the Wallets Kit module's silent `getAddress` are covered by the same check.
- The connector's positional payload (`xdr`, `authEntry`, `message`) can no longer be overridden by a same-named key in the option bag, and constructing a client with an `npm:` snap ID other than the published one logs a console warning.
- The companion dapp renders the connector bench only when `GATSBY_DEV_BENCH=true` (a release build refuses that flag), refuses `ALLOW_LOCAL_SNAP=true` for production builds (a development build must declare itself with `GATSBY_ACTIVE_ENV=development`), validates Horizon-reported transaction hashes as 64 hex characters before building an explorer link, caps Horizon response bodies at 1 MiB, and sends `Permissions-Policy` and `Cross-Origin-Opener-Policy: same-origin` headers. Its exact-version build guard now matches the connector's rule (prerelease suffixes are refused), so a version the build accepts can never throw in the page.
- The release workflow is split into a build job that runs every gate without any secret or OIDC token and a publish job that only verifies tarball digests and publishes the exact tarballs the build job packed; the manifest seal is re-verified immediately before packing and the tarball contents are compared byte for byte with the committed files. Publishing uses npm trusted publishing (OIDC) with npm 11.5.1 or later, no long-lived npm token remains (the one-time bootstrap token path is explicit, input-gated, and documented), and a real publish started manually from anything other than a release tag is refused.
- A lockfile-accurate advisory gate audits the snap's exact production dependency graph against the npm advisory database (with a registry canary), because Yarn 3's audit keys by package name across workspaces and can report another workspace's versions; the Yarn audit report must carry its expected fields before an empty advisory map is trusted; the allow-scripts inventory lists every dependency that declares an install script, the stale sharp entry is gone, and Yarn's disabled-build-script warnings are no longer discarded; and the path-to-regexp, engine.io, and socket.io-parser advisories in the site build chain are cleared through root resolutions.

- The entropy fingerprint that binds persisted state to the active Secret Recovery Phrase is computed from the parent node's public key bytes. It was hashing the key-tree hex string, whose `0x` prefix makes `Buffer.from(value, 'hex')` return an empty buffer, so every phrase produced one constant fingerprint and no phrase change was ever detected: grants and account indices recorded under one phrase stayed in force under the next, and the in-context address-cache invalidation keyed on the same value never fired.
- A change of the primary Secret Recovery Phrase is now observed by every grant-gated request, not only by the first key use of an execution context. The binding check fetches the parent node on each call (one `snap_getBip32Entropy` per grant-gated request), the persisted-state reconciliation is keyed to the observed fingerprint rather than latched once per context, signing-account resolution reads state only after the reconciliation a fetch may trigger has settled, and the home page establishes the binding before its state read, so one render can no longer combine the old phrase's grants and indices with addresses derived from the new phrase. Lifecycle tests change the mocked entropy mid-context and assert grants, account selection, and the store are reset before use.
- The companion dapp's Send and Trustline flows (and the development bench's Soroban signing) pass `networkPassphrase` with every `signTransaction` call. The wallet requires the caller to state the network on PUBLIC, so both mainnet flows were deterministically rejected before any dialog.
- The release workflow seals the connector artifact: the `dist/` tree is digested immediately after the verified build, re-checked just before packing, and the packed tarball's `dist/` entries are byte-compared against that tree, with unexpected tarball files refused and the packed `package.json` compared against HEAD. Previously only the snap tarball was compared with verified content, and the cleanliness gate cannot see the gitignored `dist/`, so post-test tooling with write access could have altered what was published.
- The connector re-verifies the pinned snap version before signing and every dialog-confirmed mutation (`signTransaction`, `signAuthEntry`, `signMessage`, `requestAccess`, `setNetwork`, `setActiveAccount`, `addToken`), instead of trusting the once-per-page memo; a snap updated under the same npm ID mid-session now fails those calls closed with the version-mismatch error. The companion site also re-reads the installed snap when the tab regains focus or visibility, so its displayed readiness tracks an update made while the page was open.
- The simulation resource-fee field is bounded to the 19 digits an int64 stroop count can occupy before conversion and display; a longer endpoint-supplied value renders as an unavailable estimate while the rest of the simulation summary is kept, so a hostile RPC can no longer feed a near-megabyte number into `BigInt` conversion and the review dialog.
- The message-signing dialog shows its warning banner and the escaped exact view whenever the message renders differently from the signed bytes, including ordinary tabs, line breaks, and collapsible spacing, matching the lossy-display rule the transaction dialog applies to `manageData`. Previously only the hidden-character class triggered it, so a site could shape a message into field-like lines with no warning and no exact representation anywhere.
- The companion dapp's Horizon helpers cancel response bodies they will not read (non-success responses in `getJson`, every status path in `accountExists`), so repeated requests against a malfunctioning endpoint no longer accumulate open streams in the page.

### Changed

- CI and the release workflow run `yarn typecheck` (`tsc --noEmit`) across every workspace. The root tsconfig enables `strict`, `noUncheckedIndexedAccess`, and `exactOptionalPropertyTypes`, but nothing ran the compiler over the snap or the site: `mm-snap build` transpiles through SWC, `gatsby build` through Babel, and typed linting reports lint rules rather than type errors, so a type error in the signing surface could land green.

- The snap home page renders from a single decrypted state read instead of four, so the page is assembled from one consistent snapshot.
- The fail-closed signing guards are covered by in-process tests against a mocked `snap` global (`src/handlers/sign-guards.test.tsx`), and `jest.config.js` carries per-module coverage thresholds that CI enforces. Those guards are each a single `if` whose removal silently widens what the snap will sign; while the module reported 0% branch coverage (an artifact of snaps-jest running the built bundle) no threshold could protect them.
- The connector compiles with NodeNext module resolution and explicit `.js` import extensions, so the shipped ESM loads under native Node, not only through bundlers; both packages publish with npm provenance; `rimraf` is replaced by Node's built-in `fs.rmSync`; the site's build scripts use `cross-env` so they run on Windows shells.
- New test suites cover the RPC router (dispatch, error laundering, throttle bookkeeping), the Horizon and Stellar RPC clients (response validation, sanitization, degradation), connector provider discovery, response-shape validators, and the Freighter facade; root `yarn test` now runs the snap and connector workspaces, and the router/Horizon/RPC modules carry coverage thresholds.

- The exact Node.js release is pinned in `.nvmrc` and every workflow installs from it; `docs/RELEASE.md` records the cross-platform reproducibility argument (a committed manifest that passes the Linux CI diff was built on Windows with a different native transpiler binary), the toolchain pin, and the one-time npm and GitHub setup; and the comments describing what `mm-snap manifest` does at publish time (validate and fail, not rewrite) and where the bundle's `Math.random` references come from are corrected.
- `WatchWalletChanges` in the connector exposes a `WalletChange` type and no longer invokes the listener inside a promise chain.
