# Threat Model — Stellar Soroban Snap

> Written 2026-08-10 for Phase 5 (pre-audit). Scope: `packages/snap` (the audited artifact) and its trust relationships. Companion artifacts (`packages/connector`, `packages/site`) run outside the snap sandbox and hold no secrets.

## 1. Assets

| Asset                                                                | Where it lives                                                                                                 | Exposure                                                                                      |
| -------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| **SEP-0005 private key** (`m/44'/148'/x'`, ed25519)                  | Derived on demand from MetaMask's SRP via `snap_getBip32Entropy`; held only in function scope during a request | Never persisted, never returned via RPC, never sent over the network; no export method exists |
| **Signatures** (tx envelopes, Soroban auth entries, SEP-53 messages) | Produced in-request, returned to the calling dapp                                                              | Only after an explicit per-request user confirmation                                          |
| **Snap state** (`snap_manageState`, encrypted)                       | Active network, account registry (SEP-5 indices), per-origin grants, tracked tokens, entropy fingerprint       | No key material; encrypted by MetaMask with a snap-specific key                               |
| **User's addresses**                                                 | Derivable on demand for every user-revealed account index                                                      | Disclosed only to origins with a standing grant (or empty string)                             |

## 2. Trust boundaries & actors

```
[dapp origin]  --wallet_invokeSnap-->  [MetaMask]  --sandboxed-->  [snap (SES)]
                                                                     |  fetch
                                                     [Horizon / Stellar RPC endpoints]
```

- **Dapp (untrusted).** May send arbitrary method calls, malformed params, hostile XDR, and misleading claims about what a transaction does. Mitigations: superstruct validation on every method (§4.1); all display derived from parsed XDR, never dapp summaries (§4.2); per-origin grants; per-request confirmations; SEP-43 error sanitization (internal errors are replaced by a generic message so internals never leak).
- **MetaMask platform (trusted).** Supplies `origin` (the snap cannot verify it independently), the entropy API, dialogs, and state encryption. The SES sandbox and permission caveats (`m/44'/148'`/ed25519 only) are platform-enforced.
- **Network endpoints (semi-trusted, availability-untrusted).** Horizon and Stellar RPC responses drive _display aids only_: simulation results, safety warnings, balances. A malicious/compromised endpoint could suppress warnings or show wrong fees/balances — it can never alter what is signed, extract keys, or forge approval. Endpoint URLs are hardcoded per network (not dapp-supplied). See §5 residual risks.

## 3. Security claims (what an audit should try to break)

1. **No key exfiltration.** Private keys exist only inside `deriveKeypair` callers' scopes; there is no RPC method, log, state write, or network call that carries key material.
2. **Display integrity.** What the confirmation dialog shows is derived exclusively from the XDR that will be signed (`TransactionBuilder.fromXDR` / `xdr.SorobanAuthorizationEntry.fromXDR`). Anything that cannot be displayed in full fails closed before a dialog is shown: unknown operation types, unknown host functions, unknown credential/function/ScVal variants, claimable-balance conditions of an unknown variant or nested beyond the rendering bound, and any Soroban value or authorization tree whose rendering hits a depth, item, byte, string-length, or entry limit are rejected rather than shown as an opaque or truncated label (the one deliberate exception: an uploaded wasm blob is identified by its SHA-256, a cryptographic commitment). The snap never signs bare hashes: SEP-53 and Soroban auth preimages are reconstructed from parsed structures.
3. **No signature without consent.** Every signing path (`signTransaction`, `signAuthEntry`, `signMessage`) passes through `snap_dialog` and throws SEP-43 `-4` on rejection. `getAddress` is the only silent method and returns `''` without a grant.
4. **Network passphrase pinning.** Transactions/auth entries are parsed and signed against the active network's passphrase; a dapp-supplied mismatching passphrase is rejected (`-3`), preventing cross-network replay confusion.
5. **The snap never mutates what it signs.** Simulation and safety checks are read-only display aids; the signed bytes are exactly the dapp-provided XDR plus the appended signature.
6. **No insecure randomness.** `Math.random` is rewritten to `crypto.getRandomValues` at bundle time (webpack plugin in `snap.config.ts`); the shipped bundle contains zero `Math.random` occurrences. (Key derivation involves no local randomness at all — it is deterministic from the SRP.)
7. **Bounded account resolution.** The SEP-43 `address` option resolves only against the explicit registry of user-revealed account indices (`state.accounts` in `resolveSigningKeypair`); a dapp can never cause derivation or a signature for an index the user has not added. Accounts are revealed one contiguous index at a time from the snap home page after a confirmation dialog, and `setActiveAccount` activates only revealed indices. Every signing dialog names the resolved account ("Account N") next to its address, so a dapp selecting a non-active account stays visible. Selecting any account other than the active one requires a standing grant, and that check runs before resolution, so an ungated origin cannot use the outcome to probe which addresses the wallet holds.

Two manifest values worth an auditor's explicit attention, since neither is self-explanatory and JSON carries no comments:

- **`maxRequestTime: 60000`** (reduced from 120000; the platform maximum is 180000). The timer covers the user's review time for a signing dialog, and a complex Soroban confirmation with a full footprint takes real minutes to read, so it cannot be tightened to a few seconds. The interaction to note is with the in-flight budgets in `src/rpc/limiter.ts`: an origin can hold `MAX_INFLIGHT_PER_ORIGIN` (4) request slots for the whole of that window, and holding one is cheap, because MetaMask serializes snap dialogs (a request queued behind another site's dialog stays in flight without the caller doing anything) and `signMessage` reaches its dialog after only a key derivation. The window is what converts held slots into a denial-of-service duration, so it is treated as a security parameter and not merely a usability one: the platform maximum was rejected because "the largest value allowed" is not a justification. It was subsequently halved again, to 60000, on the same reasoning applied one step further. The longest legitimate request is bounded by the user's reading time plus at most one 10-second simulation and a set of parallel 5-second Horizon lookups, so 60000 still sits well beyond any observed review while halving the denial-of-service duration a held slot buys.

  The per-origin cap is self-limiting: an origin spending its four slots denies service to itself. `MAX_INFLIGHT_GLOBAL` (32) is not, because it is shared and is checked first, so a site rotating subdomains could once fill every slot and leave every _other_ dapp refused for the whole request window. That is why the global ceiling is split by connection grant: origins without a standing grant stop at `MAX_INFLIGHT_UNCONNECTED` (8), leaving the remainder reachable only by origins the user has approved, which an attacker cannot join silently since a grant requires an approved dialog. This mirrors the `MAX_PREDIALOG_UNCONNECTED` split described below, for the same reason and with the same residual: a legitimate first-time dapp calling cold during an attack draws on the unreserved share and can still be refused.

  Be honest about what the unconnected share buys, because it is easy to overstate. It does not stop the attack; it sets how many distinct origins the attack needs (`share / MAX_INFLIGHT_PER_ORIGIN`, so two at the current values), and subdomain rotation makes an origin nearly free. Its real work is bounding the blast radius to _unconnected_ callers while the reserved headroom keeps approved sites serviceable, and shrinking the share costs a legitimate cold caller nothing, since MetaMask serializes dialogs and an honest unconnected dapp never has more than one or two requests in flight. The durable bound on this class of attack is `maxRequestTime`, which caps how long a held slot stays held.

- **`snap_getBip32Entropy` is scoped to `m/44'/148'` on ed25519**, not a wildcard. Coin type 148' is the only reachable subtree, the account-level hardened index is derived in-snap, and the bound on that index is re-asserted at the derivation primitive itself (`deriveFromNode`) rather than only at callers, so an index escaping state validation cannot become a key.

Test anchors: SEP-5 official vectors (indices 0 to 2), cryptographic verification of every signature type against the derived public key, SEP-43 error codes, dialog-content assertions, persisted-state schema validation (including that every pre-version-2 shape resets rather than migrating), account add/switch/resolution flows, entropy-request counts on the derivation path, entropy-binding reconciliation, contract-metadata bounds checking, balance-change decoding (including asset-name impersonation and every partial-summary trigger), review-dialog fidelity (raw-byte rendering of ASCII-decoded fields, trustline removal, source-account and fee-source disclosure, claim-predicate rendering, simulation provenance), and home-page consent interactions (553 snap tests across 27 suites, plus 64 connector tests).

Coverage (`yarn workspace stellar-soroban-snap test:coverage`, and the same script in the connector) reports 80.1% statements / 67.9% branches for the snap. **Read the figure with care: it still understates coverage and is not a quality measure.** snaps-jest executes the built `dist/bundle.js` inside the snap execution environment, so anything driven through `installSnap` produces no instrumented coverage of `src`, and every module reachable only that way reports near-zero branch coverage however thoroughly it is tested. The modules with real instrumented coverage are those exercised in process, either as pure functions (`state`, `keys`, `ui/format`, `stellar/soroban`, `rpc/validation`) or by calling a handler directly against a mocked `snap` global.

`handlers/sign.tsx` is now in the second group (`src/handlers/sign-guards.test.tsx`), which matters for more than the number. The module is a dozen independent fail-closed guards, each a single `if` whose removal silently widens what the snap will sign and looks like nothing in review. While it reported 0% branches no threshold could protect any of them; it now reports 83% statements / 62% branches, and `jest.config.js` carries per-module `coverageThreshold` entries that CI enforces, so a deleted guard fails the build. The suite includes two positive controls (cold signing reaching a dialog, and a classic payment signing end to end) so the guard assertions cannot pass for the wrong reason, and it asserts on submission-integrity behaviour as well: a returned hash that does not match the signed envelope is refused, and a failed submission still returns the signed envelope for the dapp to retry.

Property tests back claim 2 specifically: `src/stellar/soroban-fuzz.test.ts` and `src/ui/transaction-fuzz.test.tsx` drive randomized ScVals, authorization trees, host functions, transactions, and byte-mutated envelopes through the decoders and the dialog builder, asserting on every case that nothing throws unhandled, that no rendered inline text carries control, bidi, or zero-width characters, that every visible truncation also sets the flag the signing paths refuse on, and that the raw XDR stays on offer. Generation is seeded over a fixed range, so the corpus is identical on every run and a failure reports the seed that produced it. A corpus-coverage assertion pins how many cases actually reach truncation, escaping, and nesting, so the invariants cannot quietly become vacuous.

## 5. Residual risks & accepted trade-offs

- **Display-aid trust in endpoints.** Simulation results, resource-fee estimates, and safety warnings are only as honest as the configured Horizon/RPC endpoints (SDF testnet; Gateway.fm mainnet). Failure mode is bounded: warnings are advisory, absence of a warning is never presented as "verified safe", and simulation failure renders an explicit "unavailable" banner. The mainnet Soroban RPC being a third-party gateway is an explicit trust choice (SDF operates no public mainnet RPC). It can never alter what is signed, which is the property that matters most, but the trust placed in it is broader than display: **the same endpoint is the submission path** for Soroban transactions on PUBLIC (`sendTransaction` in `handlers/sign.tsx`), so it is handed the signed envelope itself. A malicious gateway can therefore (a) skew advisory display, (b) deny `signAuthEntry` on PUBLIC, since its expiry bound fails closed when the ledger is unreadable, and (c) accept a submission, return the correct hash, pass the snap's hash-match check, and never broadcast, retaining a valid signed mainnet transaction it may broadcast later or not at all.

  What it can **no longer** do is set an authorization's lifetime on its own. The `signAuthEntry` expiry bound is `Math.min` over the ledger heights that answered, and a minimum over one value is that value, so "take the minimum of the sources we can reach" used to become "trust whichever source answered" whenever the other one did not. Horizon returning 429 under load was enough to reach that state, and the consequence was not a missing check but a wrong disclosure: a gateway overstating the height would stretch the real lifetime of the authorization while the dialog reported a duration computed from the same inflated number, so "expires in ~5 min" could sit over an entry valid for as long as the gateway cared to claim. `handlers/sign.tsx` now requires **both** sources to answer on every network and refuses with a distinct message when only one does. Test networks are not exempt: every reported height is bounded to a positive `uint32` at the response boundary (`stellar/ledger.ts`, shared by the RPC and Horizon parsers, and re-checked by `boundAuthExpiration` before it does arithmetic on the value), but range validation limits what a sole source can claim without telling an inflated in-range height from a real one, so the independent confirmation is the only check that catches it, and leaving that to the network the wallet happens to be on would let a sole test-network RPC set the default lifetime by itself. The residual is availability: either endpoint being unreachable denies `signAuthEntry`, which is the same fail-closed direction the path already took for an entirely unreadable height. The hash check (`assertSubmittedHash`) is what prevents a gateway from misreporting a _different_ transaction as the submitted one; it cannot detect non-broadcast, because a correct hash for a withheld transaction is indistinguishable from one for a pending transaction. This compounds with an envelope carrying no upper time bound, which is why the dialog now states plainly when a signature never expires.

  Mitigations in the product rather than the code: the review dialog names the host that will receive the envelope whenever `submit` is requested, and says it can delay or withhold the submission, so a user choosing one-click submit on mainnet can weigh who mediates it. A dapp that prefers not to rely on the gateway can omit `submit` and broadcast the returned `signedTxXdr` through its own infrastructure, which is the SEP-43 default. Operationally, the endpoint is a hardcoded constant inside a shasum-sealed artifact, so it cannot be rotated without a new release and re-allowlisting: re-verify it at every release, and treat its compromise or discontinuation as an event with a slow remediation path.

  **Token metadata is the one gateway answer that persists.** Everything else the gateway says is consumed once and discarded, so a lie lasts exactly as long as the dialog it appears in. `addToken` is different: it reads `symbol` and `decimals` by simulation (`stellar/token.ts`), and both are then written to state and reused for every later balance render, on the home page and through `getBalances`, without ever being re-read. `decimals` is the one that matters, because it is a scale factor: a gateway that returns a wrong-but-plausible value for a genuine contract makes every future balance for that token render at the wrong magnitude, persistently, from a single answer at tracking time. `sanitizeTokenMetadata` bounds both fields (printable ASCII, at most 12 characters; decimals 0 to 38), which stops the display being spoofed or the formatter being hung, but a bound is not a cross-check: it cannot tell 7 from 6. The compensating controls are that tracking a token requires a user confirmation naming the contract, that `formatTokenAsset` always renders the contract address beside the symbol so a token calling itself `XLM` stays distinguishable from the native balance row, and that the `type`/`contractId` fields carry that distinction across the RPC boundary so a dapp need not parse it out of a display string. The residual is a misreported balance magnitude, not a misdirected payment: no signing path reads this value, and payment amounts come from the envelope, never from a token's stored `decimals`. The SAC half of the gap is now closed at the write (2026-08-20 audit, `SECURITY_AUDIT2.md` finding L-01): a Stellar Asset Contract's decimals are fixed at 7 by the protocol, so on a contract `addToken` has verified as that asset's SAC the reported value is checkable, and a mismatch can only come from a lying endpoint. `addToken` refuses it (`SAC_DECIMALS` in `stellar/events.ts`, the same constant the balance-change summary already scales verified SACs by, so state and the signing dialog can no longer disagree about the same asset's magnitude), and refusal is the right arm rather than repair: an endpoint proven to lie about a derivable value cannot be trusted for the symbol from the same response either, and an honest endpoint can never trip the check. For arbitrary SEP-41 contracts there remains nothing to check the value against; re-reading metadata on a schedule would narrow that residual and is not implemented today.

  **Decision (2026-08-15): accepted as-is, deliberately.** The 2026-08-15 security audit (`SECURITY_AUDIT.md`, finding I-3) raised this for a decision and offered two alternatives: polling Horizon for the hash after a `PENDING` `sendTransaction` on PUBLIC, so that "broadcast and pending" could be distinguished from "accepted and withheld"; or refusing `submit` on PUBLIC outright, leaving dapps to broadcast the returned `signedTxXdr` themselves. Both were declined. One-click mainnet submit is a product requirement, the confirmation poll adds latency and another outbound dependency to the one path where latency is most visible, and refusing `submit` is a breaking API change for conformant callers. The disclosure in the review dialog stands as the mitigation: it names the receiving host and states plainly that the host can delay or withhold the submission, which is the fact a user needs in order to decide. Revisit if the gateway's operator, terms, or reliability change, since the residual is concentrated entirely in that one relationship.

- **Balance changes are evidence, not an accounting.** The balance-change section of a Soroban dialog (`stellar/events.ts`) is decoded from the token events the simulation reports, and it inherits the endpoint trust above plus one of its own: the events are emitted by a contract the dapp chose. Three limits are therefore stated in the dialog rather than left to inference. It can **under-report**, because a token contract is free to move balances without emitting a SEP-41 event at all, which is why an empty result renders a sentence saying no movement was reported and that this is not a guarantee, never an absent section. It can be **incomplete**, because an undecodable event or a cap (100 events, 12 distinct assets) drops a movement, which raises a banner rather than shortening the list quietly. And it can be **padded**, because any contract may emit a `transfer` crediting the user with a token it invented, so a drain can be dressed as a swap: the compensating property is that the debit row for the real asset still appears, and an invented token can never borrow a real asset's name, since an asset name is displayed only when the emitting contract is that asset's Stellar Asset Contract at the address the snap recomputes for the active network. Unverifiable tokens render as `Token C…` with amounts in the smallest unit, so a fabricated credit cannot present itself as a familiar asset or at a flattering magnitude. Nothing here reaches a signing path: the section is display only, and the transaction signed is the envelope the dapp supplied, unchanged.
- **Response-body bounding.** `readJsonBounded` checks the declared `Content-Length`, then consumes the body incrementally through the response stream and aborts the moment the byte cap is exceeded. When the runtime exposes no body stream, a buffered fallback still enforces the cap after decoding; in that degraded mode a hostile endpoint omitting the header can buffer up to its full body before the cap throws (denial of service of the snap only, requiring a compromised hardcoded endpoint, bounded by the abort timeout).
- **Test reset hooks ship in the bundle (accepted).** `resetAddressCache`, `resetRequestLimits`, `resetDialogThrottle`, and `resetBalanceCache` are exported from production modules, and between them they clear every in-memory control the snap has: the entropy binding, the rate limits and in-flight budgets, the dialog-fatigue cooldowns, and the balance coalescing cache. They exist because that state outlives a test otherwise, and there is no build-time strip that both `mm-snap build` and `ts-jest` would honour without a second build path, which is a worse trade than the exposure. The exposure is nil today and the reason is structural, not incidental: the snap's entire external surface is the handlers exported from `src/index.tsx`, and dapp-reachable dispatch goes through a fixed `HANDLERS` table in `rpc/router.ts` looked up with `Object.prototype.hasOwnProperty`, so a caller cannot name a function that is not in that table. **The invariant to preserve is therefore the table, not the exports:** any future dispatch keyed on a caller-supplied name, anywhere, would need to re-examine this. See the 2026-08-15 audit, finding 8.
- **`origin` string trust.** Origin gating relies on MetaMask's origin reporting; the snap cannot independently verify it. Platform-standard assumption for all snaps.
- **Per-origin controls are bypassable by origin rotation (bounded by a global budget).** Every rate limit, in-flight budget, and dialog cooldown in `src/rpc/limiter.ts` and `src/rpc/throttle.ts` is keyed on `origin`, and the snap cannot tell `a1.example` from `a2.example`. A site controlling a wildcard domain therefore gets a fresh per-origin allowance per subdomain. Two mitigations bound what that buys. First, the tracking maps evict the _least recently used_ entry rather than the oldest-inserted, so an attacker rotating origins can no longer evict an active origin's counters, nor clear the record of its own cooldown by making further requests (the refused path refreshes recency too). Second, the network lookups that run _before_ any dialog draw on a single global, origin-independent budget (`takePredialogBudget`, `MAX_PREDIALOG_LOOKUPS`). That budget is what survives rotation. Its call sites are enumerated here rather than described in general terms, because a lookup that forgets to claim it is invisible in review and silently reopens the amplification path: the Horizon account checks in `src/stellar/safety.ts` (`collectSafetyWarnings`, `collectFeeSourceWarnings`), the display-verification simulation in `simulateForDisplay`, and the two ledger-height reads in `signAuthEntry` (`getLatestLedger` plus `getHorizonLatestLedger`, which claim two slots together). The `signAuthEntry` reads sit behind a connection grant, since an address-credential entry always names its authorizing account and naming any account requires a grant, so they were never on the cold-callable surface; they claim the budget anyway, because the budget bounds total outbound work against shared community infrastructure and not merely the unauthenticated share of it. It matters because `signTransaction` is callable without a grant (see "Cold signing surface") and fans out up to seven Horizon lookups per call, which would otherwise make the wallet an unauthenticated amplifier against shared community infrastructure. Denial of the budget is deliberately neither an error nor silent for the _advisory_ callers: they fall through to their existing "could not check" paths, which state in the dialog that the checks did not run. Throwing would let an attacker drain the budget to block a legitimate signature; failing silently would let them drain it to suppress a real warning. A visible caution is the only option that is not exploitable in one direction or the other.

  A **second** global budget covers the one remaining bulk fan-out: `takeTokenReadBudget` (`MAX_TOKEN_READ_LOOKUPS`), claimed by `readBalances` in `src/handlers/account.tsx`. `getBalances` runs one simulation per tracked token, so a single call can cost up to 30 round trips against the shared Soroban RPC, and its 15/minute rate limit permits roughly 450 a minute; the 5-second coalescing cache does not bound that, because it is keyed by address and a connected origin learns every revealed address from `getAccounts`.

  It is a separate pool rather than a second claim on the pre-dialog budget, and the separation is the point. The pre-dialog pool holds 120 slots, so a wallet tracking 30 tokens would drain it in four `getBalances` calls, and an ordinary polling dapp would then degrade the user's _signing_ dialogs to "safety checks were skipped" purely as a side effect of refreshing balances: the same permanent, universal caution this section argues is worse than no caution. Two pools keep availability of the balance display and integrity of the signing disclosure off one meter. Denial of the token budget omits the token rows and sets `tokensUnavailable` on the result, so a dapp cannot read a short list as "this account holds none of these tokens". The snap home page runs the same fan-out and deliberately does **not** claim: it is reachable only by the user opening their own wallet UI, so there is no origin to bound, and making it draw on the pool would hand a connected dapp a way to blank the balance rows the user checks their wallet with.

  The `signAuthEntry` ledger reads are the deliberate exception: there, denial _is_ an error. The ledger height is not a display aid, it is what bounds how long the signature stays valid, and that path already refuses to sign when the height cannot be read at all. Degrading to a caution would mean signing an authorization whose lifetime the snap never verified, so it takes the same fail-closed exit as an unreachable endpoint, with a distinct message so a user can tell "retry in a minute" from "the endpoint is down".

  **The budget is split so draining it cannot silence other sites.** A single undifferentiated pool has a second-order problem the paragraph above does not cover: the claim happens _before_ any dialog opens, so it needs no user interaction, and one site rotating subdomains can empty the pool in seconds. Every _other_ site's signing dialog then renders the "checks were skipped" advisory for the rest of the window, sustainably, by re-firing each minute. A caution an attacker can make permanent and universal is not a caution: it becomes noise the user learns to click past, which is precisely the state in which a real unfunded-destination or SEP-29 warning goes unread. The fix does not try to tell rotated subdomains apart, because it cannot. It splits the pool by connection grant instead: origins _without_ a grant are capped at `MAX_PREDIALOG_UNCONNECTED` (60, exactly the budget the cold surface had before the split, so the anti-amplification bound on the unauthenticated surface is unchanged), while origins holding a grant may draw on the full `MAX_PREDIALOG_LOOKUPS` (120). The reserved half is reachable only by origins the user has already approved, and an attacker cannot join that set silently, since a grant requires an approved dialog. Residual: a legitimate first-time dapp cold-signing during an attack draws on the unreserved share and can still be denied, degrading to the same visible caution as before. `handlers/sign.tsx` reads the grant once per request and threads it through `collectSafetyWarnings`, `collectFeeSourceWarnings`, and `simulateForDisplay`; all three default the flag to "unconnected", so a caller that omits it lands in the cold share rather than silently reaching the reserved one.

- **Pre-dialog lookups disclose attacker-chosen content to third parties before any user action (accepted).** `signTransaction` is cold-callable, and its display-verification simulation and Horizon safety lookups run _before_ the review dialog exists. So any page the user visits can, with no user interaction and no prior grant, cause the wallet to send an attacker-authored envelope to the Soroban RPC and attacker-chosen account addresses to Horizon, from the user's IP. On PUBLIC the RPC recipient is the third-party gateway.

  What this does and does not cost. The envelope is authored by the attacker, so the endpoint learns nothing about the user's holdings from its contents; what leaks is the correlation, meaning the user's IP address alongside the fact that this wallet was asked to consider a specific transaction. It also makes the snap a modest unauthenticated relay, bounded at `MAX_PREDIALOG_UNCONNECTED` (60) lookups per minute across every unconnected origin.

  **Decision (2026-08-15): accepted, not gated.** The obvious fix is to require a connection grant before any pre-dialog lookup. It was rejected because it trades a privacy leak for a safety one, in the direction that matters more: a first-time dapp requesting a mainnet payment is exactly the case where an unfunded-destination or SEP-29 memo warning is most valuable, and gating would replace those warnings with "safety checks were skipped" for every cold caller, permanently, in normal operation. That is the same "a caution that is always present stops being a caution" argument this section makes about budget exhaustion, applied to the cold path. The bound above, plus `redirect: 'error'` and the fact that the endpoints are hardcoded constants, is what makes the residual acceptable. Revisit if the snap ever gains a user-configurable RPC endpoint, since the recipient would then no longer be a fixed, auditable party.

- **Address display derives private key material (accepted, with a named alternative).** Every address the snap shows comes from a full keypair derivation: `getAccountParentNode` fetches the SEP-5 parent node, which carries the private key for the whole `m/44'/148'` subtree, and `deriveFromNode` materializes each child's private key. The consumers include paths that need only a public key: the home page, `getAccounts`, `getAddress`, `requestAccess`, and `findAccountIndexByAddress`. `deriveFromNode` now zeroes the seed copy it creates once `Keypair` holds its own (verified against @stellar/stellar-sdk 16.2.0, and guarded by a canary test in `src/keys/index.test.ts`), so it leaves one fewer reachable copy behind than it creates, but the parent node still exists for the lifetime of the request.

  **Decision (2026-08-15): not changed now.** `snap_getBip32PublicKey` is authorized by the same `snap_getBip32Entropy` permission already declared and would return public keys without exporting private material, so the alternative is real. Three things argue against making the switch as a security fix rather than a considered change. It derives one path per call, so `findAccountIndexByAddress` (a bounded sweep of up to 256 indices, and the flow that exists so a user can reach an account they hold in another SEP-0005 wallet) becomes up to 256 platform round trips. The entropy binding in `bindToEntropySource` fingerprints the parent node's public key, so removing the parent-node fetch from display paths removes the check that invalidates the address cache when the primary secret recovery phrase changes, and that check would have to be rebuilt on the new API before anything else moved. And the gain is narrow: the signing path fetches the parent node in the same execution context anyway, so the exposure is reduced for read-only sessions rather than eliminated. Revisit as a deliberate refactor with the entropy binding moved first, not as a patch.

- **Network state is readable before connection (deliberate).** `getNetwork` and `getNetworkDetails` are callable by any origin with no grant and no dialog (they carry a per-origin rate limit of 120/minute, which bounds polling but is not a gate), unlike `getAddress`, which returns `''` for unconnected origins specifically to avoid a fingerprinting signal. This is Freighter/SEP-43 parity: dapps routinely read the active network to decide whether to prompt at all, and the connector's `WatchWalletChanges` polls it on an interval from before the first connection. What it discloses is low-sensitivity and largely already public: the endpoint URLs are hardcoded constants readable in the published bundle, and the network name is a three-value enum. The residual is a correlation signal, since two unconnected sites observing the same network transition at the same moment have evidence they are looking at the same wallet, plus confirmation that the snap is installed to origins that never requested a connection (already obtainable from `wallet_getSnaps`). Gating these would break conformant dapps for a marginal privacy gain, so it is accepted rather than fixed.
- **`networkPassphrase` is optional in SEP-43, and is now required on PUBLIC (fixed).** When a dapp supplies `networkPassphrase`, a mismatch with the active network is rejected (`-3`), which is claim 4 above. When it omits the field, there is nothing to mismatch: the envelope is parsed and hashed against whatever network the wallet is on. The asymmetry that matters is directional. A dapp intending PUBLIC while the wallet sits on TESTNET gets a signature that is worthless on mainnet, which is the safe direction. A dapp intending TESTNET while the wallet sits on PUBLIC gets a **mainnet-valid signature**, and neither party has stated a network anywhere in the exchange.

  This was accepted for a time, on the grounds that SEP-43 makes the field optional and that every PUBLIC signing dialog already carries an unconditional "Mainnet: this transaction will move real funds on PUBLIC" banner. The reason it is no longer accepted is that the banner is a weak defence for this specific case. The user is not being asked to evaluate a claim the snap made; they are being asked to notice a network _they_ set in an earlier session and that the site never mentioned, and nothing in the exchange creates the expectation that this is the request worth re-checking. "The disclosure is the only defence" was the recorded residual, and a single conditional removes it.

  `assertNetworkStated` in `src/handlers/sign.tsx` now refuses `signTransaction` and `signAuthEntry` with `-3` when the active network is PUBLIC and no passphrase was supplied. Scoped to PUBLIC deliberately: test-network ergonomics are untouched (no development workflow changes, and the suites still omit the field everywhere else), and a conformant mainnet dapp necessarily already holds the passphrase, since it built the envelope with it. Asserted in `src/handlers/sign-guards.test.tsx`, including the positive control that stating the passphrase still reaches the dialog, so the guard bounds the omission rather than the network.

- **Multisig heuristic.** The insufficient-weight warning compares against the medium threshold only — not a per-operation threshold analysis. It can under- or over-warn; it never blocks.
- **Muxed accounts are not checkable (disclosed, not silent).** Horizon's accounts endpoint takes a classic `G...` address, so a muxed (`M...`) destination, operation source, transaction source, or fee-bump fee source cannot be looked up for existence, SEP-29 memo requirements, or signature weight. These are not dropped: `collectSafetyWarnings` and `collectFeeSourceWarnings` emit an explicit "NOT checked" advisory naming how many were skipped, in the same voice as the lookup-budget advisory. The rule the module holds to is that absence of a warning must never be readable as a passed check, and muxed destinations are common in exchange and custodial flows, which is precisely where the SEP-29 warning carries the most weight.
- **Horizon failure is disclosed, not silent (fixed).** A Horizon error status, timeout, or malformed body used to make `getAccountChecks` return null and the consumer skip that account without a word, so an outage produced zero warnings, indistinguishable from a transaction that was checked and found clean. Both `collectSafetyWarnings` and `collectFeeSourceWarnings` now emit the same "Safety checks were skipped" advisory for the accounts a lookup did not cover, naming how many. The checks stay advisory: an unreachable Horizon never blocks signing.
- **The transaction source is compared with the signing account (fixed).** `Source` and `Signing with` were both shown in full, but nothing said when they differ, and two 56-character strings are not something a person diffs by eye. The review dialog now raises a banner when the transaction source, any operation source, or a fee bump's fee source is not the signing account (muxed addresses compared at the base account), so a request to co-sign another account's envelope reads as such. Sequence-0 challenges are exempt, since a SEP-10 challenge is sourced from the server by design and that branch already states that nothing executes.
- **Fields the SDK decodes as ASCII are rendered from their signed bytes (fixed).** `manageData` keys and `setOptions` home domains are decoded by the SDK with an ASCII decoder that drops the high bit of every byte, so a key of non-ASCII bytes decoded to a clean ASCII word that passed every hidden-character check while differing from what is signed. Both are now rendered from the raw XDR through the same lossless text-or-hex path the `manageData` value always used, with a banner when the bytes are not plain text. Text memos take the same path, so a memo that is not valid UTF-8 (which the decoder maps to U+FFFD, collapsing distinct byte strings) is shown as exact hex with the lossy-display banner.
- **Simulation figures are labelled as endpoint-reported (fixed).** Balance changes, the resource fee, and the required signers appear under a "Simulation" heading that now names the RPC host and states that the wallet cannot independently verify the figures (on PUBLIC that host is a third-party gateway). An absent fee estimate renders as unavailable rather than as `0 XLM`, which would have claimed the call is free.
- **Token symbols are presented as self-reported (fixed).** The add-token dialog labels the symbol as the contract's own claim, states that it is unverified, and names the contract address as the only identity it can vouch for. When the contract's self-reported `name()` is `CODE:ISSUER` (or `native`) and the Stellar Asset Contract address derived for that asset on the active network is the contract being added, the dialog states the classic asset as verified; any other contract gets no such line. Address labels in token rows keep six characters on each side rather than four, and every balance-change row is accompanied by its full identity (complete contract address or `CODE:ISSUER`) in a copyable field, since a shortened address is exactly what a lookalike contract is ground to match.
- **`submitUrl` is refused by policy (deliberate).** SEP-43 lets a dapp name the endpoint the wallet should submit to. This snap submits only to its hardcoded HTTPS endpoints for the active network: a submission endpoint receives the signed envelope and can withhold or delay it, and accepting one from the requesting site would hand that trust to whoever asked. A request carrying `submitUrl` is refused with `-3` and a message that names the policy, so a conformant caller can tell it from a malformed request; the connector refuses it client-side with the same code before MetaMask is contacted. `signMessage` accepts the SEP-43 `networkPassphrase` option and compares it when present (a SEP-53 signature is not network-bound, so it is not required).
- **A rebuilt store is announced (fixed).** A persisted store that did not match the schema, or a change of primary Secret Recovery Phrase, resets grants (and, for an unreadable store, the account registry and the network preference) to defaults. That used to happen in silence. The reset now carries a one-time notice that the home page shows and clears, naming what was dropped and what was kept.
- **Balance cache is process-global and shared across origins (no security impact).** `getBalances` coalesces lookups into a 5-second window keyed by `network address` (`src/handlers/account.tsx`), so two connected origins requesting the same account share one in-flight request and can each receive data up to 5 seconds stale. Only accounts the wallet itself holds are ever queryable, so the cache cannot disclose anything an origin could not request directly, and a failed lookup evicts its own entry rather than being served for the rest of the window. Recorded because it is shared mutable state reachable from more than one origin, which is worth an auditor's attention even where the conclusion is benign.
- **Auto-grant on approved signature (deliberate).** Approving a signing dialog also records a connection grant for that origin. Our position: a signature approval is a strictly stronger act of consent than a connection approval, so deriving the weaker grant from the stronger one confers no authority the user has not already given, and the alternative (a second, redundant dialog immediately after the first) degrades consent quality by training users to click through. The dialog names the origin prominently, so the consent is informed. What the grant actually enables is narrow: silent `getAddress` for that origin, plus the `getBalances`/`fund`/`addToken` companion methods. It never enables signing, which always requires a fresh per-request confirmation. The address disclosed by a grant was already visible in the dialog the user just approved, so the marginal disclosure is nil. Grants are enumerable and revocable by the user at any time from the snap home page (Connected sites, then Disconnect), and revocation returns `getAddress` to `''`.

  Two consequences of the auto-grant are handled in the state layer. It makes the registry grow without the user ever choosing to connect anything, so `connectOrigin` caps it at `MAX_TRACKED_GRANTS` (100) and drops the least recently connected, which only means that origin must call `requestAccess` again; the same cap is applied at the parse boundary, where it prunes rather than resetting the store, since a schema-level bound would fail validation and take the account registry with it. And recording the grant must never be able to undo the signature that triggered it: `connectOrigin` runs best-effort in all three signing handlers, because it sits between the approval and `tx.sign()`, where an unguarded state-write failure would consume the user's approval and return a generic `-1`.

- **Cold signing surface (SEP-43 parity — deliberate).** `signTransaction` and `signMessage` are callable by origins without a standing grant; the confirmation dialog itself is the consent (matching Freighter/SEP-43 semantics, where dapps may request a signature without a prior `requestAccess`). `signAuthEntry` is **not** on this surface, and the distinction is easy to get wrong in review: an address-credential entry always names its authorizing account, naming an account is account selection, and selection is gated (see "Account selection is gated, signing is not" below), so every `signAuthEntry` call reaches `assertConnected`. That is asserted by `src/handlers/sign-guards.test.tsx`, not merely intended; a change that "restores parity" here would reopen the membership oracle that gating exists to close. The residual exposure is dialog-fatigue phishing: a hostile site can summon signing dialogs cold. Mitigations: every dialog names the requesting origin prominently; nothing is signed or disclosed without approval; rejection returns `-4` with no state change; MetaMask serializes snap dialogs (no dialog storms); and after three consecutive rejections an origin's dialog-bearing methods are refused for 30 seconds (`src/rpc/throttle.ts`, in-memory and best-effort, failing open on restart). The rejection counter alone does not reach the cheaper version of this attack: it advances only on an explicit `-4`, which needs the user to press reject, so an origin whose dialogs are simply ignored until `maxRequestTime` expires never triggers it however many it opens. The throttle therefore also counts dialogs _opened_ (`recordDialogOpened`, `MAX_UNANSWERED_DIALOGS` = 6), which advances without user action; any approval clears both counters, and the tighter rejection threshold still fires first for a user who actually rejects. Gating signing on a prior grant was considered and rejected — it would break SEP-43-conformant dapps and add a second dialog without adding consent.

  **Account selection is gated, signing is not.** Choosing which account signs (the `address` option on `signTransaction`/`signMessage`, or a `signAuthEntry` entry naming a non-active account) requires a standing grant; only the active account can be cold-signed for. Rationale: the outcome of address resolution is observable to the caller (a held address opens a dialog, a foreign one returns an error), so an ungated selection is a membership oracle: any origin could silently test arbitrary addresses against the wallet and learn which it holds, and confirm that two addresses belong to the same wallet. That is exactly the linkage `getAccounts` is gated to prevent. The check runs before resolution, so an origin without a grant gets the same error either way (`src/handlers/sign.tsx`, `assertAccountSelectionAllowed`). The option is strkey-validated at the RPC boundary on all three signing methods, the same standard `fund` and `getBalances` apply, so a value that cannot name an account is rejected before it reaches resolution and the field carries a length bound. Compatibility impact is nil in practice: a dapp that knows an address to name has necessarily connected before. Residual: an ungated origin can still distinguish "this address is the active one" from "it is not", the same single-address oracle that existed before multi-account.

- **Entropy source: the primary secret recovery phrase (bound, not assumed).** `snap_getBip32Entropy` is called without a `source`, so it resolves MetaMask's _primary_ entropy source. MetaMask supports more than one recovery phrase, and nothing in the store previously recorded which one its key-derived contents came from: the account registry names indices, and grants name origins, but "account 3" means an entirely different address under a different phrase. The address cache made this sharper, since it is memoized by index alone and feeds the display path (`getActiveAddress`, and through it `requestAccess`, `getAddress`, `fund`, and the home page) without the re-derivation check the signing path applies in `resolveSigningKeypair`.

  `src/keys/index.ts` now fingerprints the parent node on every fetch (SHA-256 of its public key: public data, no key material) and clears the cache when it changes, and records the fingerprint in state on first key use. A store whose fingerprint no longer matches has its account registry and grants reset, keeping only the network preference and the tracked tokens, neither of which is phrase-derived. The check cannot false positive, since the fingerprint is a deterministic function of the phrase. In practice it should never fire: a vault restored from a different phrase does not carry old snap state forward. It exists because the assumption was unstated and unenforced, which is the kind that breaks silently on a platform update. Recording it is best-effort, so a store that cannot be written degrades to a fingerprint saved one context later rather than to an inability to derive keys.

  The reconciliation latch is held as a **promise, settled rather than entered**. An earlier version set a boolean before awaiting the state write, which meant a single transient write failure disabled the check for the rest of the execution context: every `isOriginConnected` in that context would keep answering from a registry describing key material the wallet no longer had. It now latches only once reconciliation settles, clears the latch and the address cache on failure so the next key use retries, and (because the assignment is a read-modify-write with no `await` between the read and the write) collapses concurrent callers onto one reconciliation instead of racing several.

  The grant check is **bound to the handler's work, not only to its moment**. `assertConnected` returns an `EntropyBinding` (the fingerprint the grant was verified under, plus a state snapshot read after reconciliation and checked to carry that fingerprint) rather than a boolean, and every connected method resolves accounts through it: the address memo answers only while it still belongs to that phrase, a node fetched to fill a miss is refused unless it derives for it, the snapshot is the registry the handler reads, and the fingerprint travels into every state write (`setActiveNetwork`, `setActiveAccount`, `addToken`, the account reveals, `connectOrigin`), each of which compares it against the store inside the state lock. Handlers revalidate the binding after awaited network work and before disclosing wallet-derived data or applying a side effect (`assertBindingCurrent`). Explicit-address signing resolves through the same binding, so a phrase change overlapping the request refuses before any address is compared and a held address is indistinguishable from an unheld one. Without this, a concurrent request observing a changed primary phrase could reset the store between a handler's grant check and its later reads, and the handler would read the new wallet's active account, derive and disclose its address or balances, fund it, or open a wallet-global confirmation, all under consent given for the previous wallet. The reconciliation latch is additionally keyed by reconciliation identity (a per-reconciliation ticket), so a phrase changing away and back cannot let the older completion for the first period mark the binding verified for the second. Deterministic schedules for each connected method, each signing method with an explicit address, and the change-and-change-back sequence are in `src/handlers/access-guards.test.tsx`; the home page renders from the same binding's snapshot, so its origins, indices, and addresses always describe one wallet.

  The remaining soft spot is the branch that adopts a fingerprint that is simply _absent_, since "fresh wallet" and "wallet whose phrase changed before this field existed" are indistinguishable from the store alone. What makes that branch sound is an ordering invariant plus the absence of any migration: a grant is only ever written by `connectOrigin`, and every path reaching it derives a key (and so records a fingerprint) first, while `parseState` no longer migrates any older schema into the current one. "Grants present, fingerprint absent" is therefore not a state this version can produce. Because the branch rests on that invariant, the invariant is asserted rather than assumed, by an ordering test in `src/handlers/access-guards.test.tsx` that observes every state write during `requestAccess` and fails if any write pairs a grant with a missing fingerprint.

- **Entropy scope: the `m/44'/148'` subtree (deliberate).** The manifest requests the SLIP-10 subtree rather than a single account path, and multi-account support now uses it: any user-revealed index under `m/44'/148'/x'` is derived in-snap with the same on-demand, never-persisted discipline as index 0. (A caveat narrowed to `0'` would have forced a manifest permission change, a new shasum, and full user re-consent when multi-account shipped; keeping the subtree from day 1 avoided that.) The marginal exposure is bounded: the subtree covers only hardened Stellar accounts under coin type 148', no other coin type is reachable, and every use of the derived node stays inside `src/keys/index.ts`, which never persists or returns key material. The subtree node is fetched once per operation and reused across indices rather than re-requested per candidate, so resolving an address does not repeat the entropy request per revealed account; the index bound is re-asserted at the derivation primitive itself, so a value that escaped state validation cannot become a key. Which indices the wallet will act for is additionally bounded by the explicit account registry: indices are revealed one at a time by the user, contiguously, below a hard cap of 256.
- **Wallet-global active account (deliberate).** `setActiveAccount` mirrors `setNetwork`: dialog-confirmed, reserved for connected origins, and wallet-scoped, so a switch changes what every connected origin sees on its next `getAddress`. A per-origin active account would be more private but adds per-origin state and extra dialogs; it is deferred (docs/MULTI-ACCOUNT.md, section 6.3). The per-request `address` option remains the fine-grained control, available to connected origins.
- **Cross-account linkability via enumeration (accepted, disclosed).** `getAccounts` discloses all revealed addresses at once to a connected origin, which links them. That is inherent to an enumeration method: it requires a connection grant and returns only accounts the user explicitly added from the snap home page. The capability is disclosed at every point where a grant is created: the connect dialog and the signing-dialog grant notice both state that a connected site can list every added account (and that this links them), and the add-account confirmation repeats the disclosure. A user who keeps separate accounts to avoid correlation should not use them with the same origin. The same reasoning gates per-request account selection on the signing methods (see "Cold signing surface" above), so enumeration and probing both sit behind the grant rather than only the former.
- **Truncated identifiers in dialogs (accepted).** Inline address labels (asset issuers, token contracts, the source-account banner, the simulation auth-signer rows) truncate addresses (6+6 / 8+8 chars) for readability. Forging a vanity address matching 12–16 fixed base32 characters is computationally prohibitive, payment destinations are always shown in full via `Copyable`, and the complete raw XDR is present in every signing dialog.
- **Dependency surface.** Runtime dependencies are `@stellar/stellar-sdk` (XDR/crypto), `@metamask/key-tree` (SLIP-10), `@metamask/snaps-sdk`, and `@metamask/superstruct`. Supply-chain risk is mitigated by the audit pinning an exact commit plus lockfile, and by the manifest `shasum` sealing the exact published bundle.

  This table used to be maintained by hand and re-derived only when someone remembered to. It is now **enforced**: `scripts/check-known-advisories.mjs` reads a recursive production audit, fails the build on any vulnerable module not listed in `audits/known-advisories.json`, and re-greps the built bundle to confirm every "absent from the bundle" claim still holds. See "Transitive production advisories are gated" below.

  Presence in the dependency graph is not the same as presence in the audited artifact, so each vulnerable package is dispositioned against the built `dist/bundle.js`:

  | Package                                  | Via                                                                              | In the shipped bundle?                                                                                                                                |
  | ---------------------------------------- | -------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
  | `form-data`, `axios`, `follow-redirects` | `@stellar/stellar-sdk`                                                           | No. The snap hand-rolls its `fetch`-based Horizon/RPC client and never imports the SDK's Horizon or webauth modules, so webpack removes that subtree. |
  | `uuid`                                   | `@metamask/key-tree`, `@metamask/snaps-sdk`                                      | No. (Also pinned to `^11.1.1` in `resolutions`, so the advisory no longer appears at all.)                                                            |
  | `lodash`                                 | `@metamask/utils` (transitive of `@metamask/key-tree` and `@metamask/snaps-sdk`) | **Yes**, but pinned to a patched version and currently advisory-free (see below).                                                                     |

  `lodash` is the only vulnerable-package graph that has ever reached the published bundle, and the full monolithic build lands there: `__lodash_hash_undefined__`, the `_.template` machinery, and lodash's `Function("return this")` root-detection idiom are all present in `dist/bundle.js`. It carried two advisories, and the more serious one was **not** the prototype-pollution issue previously recorded here: GHSA-r5fr-rjxr-66jc is a **high**-severity code-injection advisory against `_.template`, which is exactly the code that ships. Both are cleared by pinning `lodash` to `^4.18.1` in the root `resolutions`, which is now done. `lodash` therefore no longer appears in the audit at all, and needs no allowlist entry; if a future advisory lands on it, the gate will refuse it as unreviewed rather than let it pass as "known", because it cannot be dispositioned as absent from the bundle.

  Nothing about the exploitability argument changes: no snap code calls lodash, and nothing passes caller-controlled property paths or templates to it. The point of the pin is that the argument no longer has to be load-bearing for a shipped high-severity advisory.

  Note also that lodash's `Function("return this")` is the bundle's only dynamic-code construct (there are zero `eval(` and zero `new Function` occurrences). It is short-circuited in practice by the preceding `globalThis`/`self` checks and would be neutered by SES regardless, but it is worth knowing it is there, and it is one more reason to prefer that this dependency eventually leave the artifact rather than merely stay patched.

  Reproduction note: a bare `yarn npm audit` at the repo root under-reports, because Yarn Berry defaults to the direct dependencies of the active workspace. Use `--recursive` for transitive dependencies, and run inside `packages/snap` (not `--all`) to exclude the Gatsby site's dev tooling, which dominates the monorepo-wide result and ships nothing.

  A second reproduction trap, which is what let this section drift: **`yarn npm audit` without `--json` prints roughly one row per package, not one per advisory.** The human-readable output listed four issues where the JSON reported thirty-two, and the one it collapsed away was the high-severity lodash `_.template` advisory above. Always read the JSON when dispositioning; the gate script does.

- **Transitive production advisories are gated, not merely documented.** The CI dependency gate ran `yarn npm audit --all --environment production`, without `--recursive`, so it audited only _direct_ dependencies. The snap's four direct runtime dependencies carry no advisories, so that gate passed unconditionally and could never fail on the transitive graph, which is where every production advisory this project has had actually lives. The table above was the real control, and it was a point-in-time human process with nothing re-running it.

  `scripts/check-known-advisories.mjs` now runs in both CI and the release workflow, after the build. It reads a recursive production audit as JSON and fails when a vulnerable module is absent from `audits/known-advisories.json`; re-greps the freshly built `dist/bundle.js` and fails when a module the allowlist calls absent turns out to be present; and refuses an `inBundle` entry that carries no written justification. An audit that did not run leaves an unparseable report, which is treated as a failure rather than as a clean result.

  The allowlist is keyed by **module**, not by advisory ID, because the property being asserted ("this package does not reach the shipped bundle") is a property of the package. Keying by advisory would turn every new axios CVE into a red build that teaches reviewers to edit the allowlist without reading it; there were 28 against axios alone at the time of writing. Keying by module means a new advisory in an already-unreachable package is silent, while an advisory in any package not yet dispositioned stops the build and demands a decision.

- **Build-chain surface (reported, not gated).** The CI audit gate covers `--environment production`, which is what ships. It said nothing about what _builds_ the artifacts, and a compromised build dependency reaches the deployed dapp and, for the snap, the bundle the shasum then seals. CI now also runs `yarn npm audit --all --recursive` as a non-blocking reporting step, so the full list is visible in every run and Dependabot has a signal to act on.

  Gating on it would be wrong, and the numbers show why: the build chain carries **35 advisories** (16 high, 13 moderate, 6 low) as of 2026-08-15, essentially all of them inside `gatsby` and its plugin chain, `eslint`, `jest`, and `@metamask/snaps-cli`. Almost none can be cleared from this repo, so a gate would leave the build permanently red and reviewers would learn to ignore it. What is gated is the thing that ships (`--environment production`), which is clean.

  Advisories that _can_ be cleared are pinned in the root `resolutions`: `svgo`, `webpack`, `yaml`, `tmp`, and `uuid`. The rest wait on upstream. `tar` (moderate) is the notable holdout, under `@lavamoat/allow-scripts`, `jest`, and `ts-jest`, where the fix is a major bump across the whole test toolchain: not worth forcing for a DoS advisory in a build tool.

  A caveat on reading `yarn npm audit` for these pins, learned the hard way on `webpack`. The tool reports advisories against the version actually installed, so it says nothing about whether a `resolutions` _floor_ is itself a safe version. webpack carries two separate build-time SSRF advisories against `buildHttp`/`HttpUriPlugin`: [GHSA-38r7-794h-5758](https://github.com/advisories/GHSA-38r7-794h-5758) (redirect bypass), patched in 5.104.0, and [GHSA-8fgc-7cc6-rx7x](https://github.com/advisories/GHSA-8fgc-7cc6-rx7x) (allow-list bypass via URL userinfo), affected `>= 5.49.0, <= 5.104.0` and patched only in **5.104.1**. A floor of `^5.104.0` therefore cleared the first while still permitting a version vulnerable to the second, and the audit stayed quiet because the installed version (5.109.2) is unaffected by both. The floor is `^5.104.1`. When adding a security pin, check the advisory's patched version directly rather than inferring it from a clean audit run.

  What bounds this for the snap specifically is stronger than the audit gate: the bundle is shasum-sealed, CI rebuilds and asserts the committed manifest matches, and `snap.config.ts` asserts an exact `Math.random` rewrite count, so a dependency change that shifts the emitted bundle fails the build rather than silently producing a new shasum. The site has no equivalent seal, which is why the reporting step exists at all.

## 6. Out of scope

- The MetaMask platform itself (SES, permission enforcement, state encryption) — report upstream.
- The Stellar protocol, SDK internals, and RPC/Horizon server implementations.
- The companion dapp and connector (no custody, no secrets; connector is a thin typed transport).
